KAPITEL 1: HIGH-LEVEL ARCHITEKTUR & VORWORT
====================================================================================================

Die vorliegende Infrastruktur ist ein heterogenes 2-Node-Virtualisierungssystem auf Basis von
Debian GNU/Linux 13 (Trixie) und Proxmox VE (PVE 9.1 bzw. 9.2). 

ZENTRALE DESIGN-ENTSCHEIDUNG (STANDALONE STATT COROSYNC-CLUSTER):
Beide Nodes werden bewusst als eigenständige Standalone-Hypervisoren betrieben. 
Hintergrund: Ein klassischer Proxmox Corosync-Cluster benötigt für quorum-basierte Entscheidungen
eine ungerade Anzahl von Stimmen (mindestens 3 Nodes oder 2 Nodes + externes QDevice). 
Bei einem 2-Node-Cluster ohne QDevice führt der Ausfall eines einzelnen Nodes zum sofortigen Verlust
des Quorums auf dem verbleibenden Node, wodurch VMs nicht mehr gestartet oder migriert werden können.
Die Entkopplung in:
- Node 1: Reine Compute- & Produktiv-Maschine
- Node 2: Unabhängiger Backup-Server (PBS) und vorgelagertes Zugangs-Gateway (Auth-Portal)
ist architektonisch extrem stabil und verhindert gegenseitige Blockaden.

AKTUELLE TOPOLOGIE IM ÜBERBLICK:
- Gateway / Router: FRITZ!Box (192.168.178.1, DNS / DHCP)
- Subnetz: 192.168.178.0/24 (Flaches Netz, 254 Host-Adressen)
- PVE 1 (Core): 192.168.178.169 (AMD Ryzen 5 5600GT, 32 GB RAM, 1 TB NVMe/SATA SSD + 1 TB HDD)
- PVE 2 (Backup & Chill): 192.168.178.2 (Intel Core i5-7500T, 8 GB RAM, 480 GB SSD)
- PBS (Proxmox Backup Server): Integriert auf PVE 2, lauscht nativ auf Port 8007
- Auth-Portal: CT 100 auf PVE 2 (192.168.178.101), erreichbar via Cloudflare Tunnel
- Gaming-Cluster: VM 110 auf PVE 1 (192.168.178.94), Docker-Stack mit Velocity & Purpur

     `otpauth://totp/Proxmox%20Lab%20Gateway:admin?secret=RYS5KSX6ELQUJE4W2T55UP2L2R23LKKL&issuer=Proxmox%20Lab%20Gateway`
   - Die Bibliothek `qrcode` rendert diese URI in ein Base64-PNG-Bild, das in der Web-GUI angezeigt wird.
   - Der Benutzer scannt diesen QR-Code mit der Google Authenticator App (oder Aegis / 2FAS).

2. Mathematische Berechnung des 6-stelligen Codes:
   - Google Authenticator teilt die aktuelle Unix-Epochenzeit (Sekunden seit 1970) durch 30:
     `T = floor(current_unix_time / 30)`
   - Es wird ein HMAC-SHA1 Hash aus dem Secret und dem Zähler `T` gebildet:
     `HMAC = HMAC-SHA1(Secret, T)`
   - Durch Dynamic Truncation wird ein 4-Byte-Wert extrahiert und modulo 1.000.000 gerechnet.
   - Das Resultat ist der exakte 6-stellige Einmalcode, der sich alle 30 Sekunden ändert.

3. Validierung im Backend:
   - Beim Login sendet der Client Passwort + den 6-stelligen TOTP-Code.
   - `server.js` verifiziert:
     * Bcrypt-Hash des Passworts (`bcrypt.compareSync`)
     * TOTP-Token via `verifySync({ token: totpCode, secret: config.totpSecret })`
     * Ein Zeitdrift-Fenster von +/- 1 Schritt (30 Sekunden) fängt geringe Uhrzeit-Abweichungen ab.

4. Session-Verwaltung & Cookie:
   - Nach erfolgreicher Validierung generiert der Server eine kryptografische Session-ID
     und setzt das Cookie `pmx_session`.
   - Alle nachfolgenden Anfragen an das Gateway prüfen dieses Cookie. Ohne gültiges Cookie
     wird sofort auf `/` (Login) umgeleitet.

7.2. ZUKUNFTS-INTEGRATION: GOOGLE DRIVE OFFSITE-BACKUP
----------------------------------------------------------------------------------------------------
[WICHTIGE ANLEITUNG FÜR DIE GEPLANTE ZUKÜNFTIGE UMSETZUNG]

Warum direkte Cloud-Anbindungen in Proxmox scheitern:
Proxmox VE unterstützt von Haus aus kein Google Drive API. PBS arbeitet mit Hunderttausenden
kleinen 4-MB-Dateien im Ordner `.chunks/`. Würde man diesen Ordner unverschlüsselt und unkomprimiert
synchronisieren, würde Google Drive aufgrund von API-Rate-Limits (maximal ~2-3 Uploads pro Sekunde)
blockieren oder Monate brauchen.

DIE PROFESSIONELLE LÖSUNG: RCLONE MIT CRYPT-MODUL AUF PVE 2

Schritt 1: Rclone auf PVE 2 installieren
```bash
ssh root@192.168.178.2
apt update && apt install -y rclone
```

Schritt 2: Google Drive und Verschlüsselung einrichten
```bash
rclone config
```
1. Neues Remote erstellen: Name `gdrive`, Typ `drive`.
   Den Authentifizierungs-Flow durchlaufen (Google OAuth Token).
2. Zweites Remote erstellen (Verschlüsselungs-Layer!):
   Name: `gdrive-crypt`
   Typ: `crypt`
   Remote: `gdrive:ProxmoxBackups/pbs-encrypted`
   Passwort: Ein sicheres Master-Passwort vergeben (gut notieren!).
   Dateinamen-Verschlüsselung: `standard`.
   -> Dadurch sieht Google NIEMALS Dateinamen, VM-Inhalte oder unverschlüsselte Daten!

Schritt 3: Automatisierungs-Skript erstellen
Datei: `/usr/local/bin/sync-pbs-to-gdrive.sh`
```bash
#!/bin/bash
set -e
# Warte auf Abschluss der PBS Garbage Collection (startet um 04:00 Uhr)
echo "[$(date)] Starte PBS Google Drive Sync..."

# Synchronisiere den Datastore
rclone sync /mnt/pbs-storage/ gdrive-crypt:/ \
    --fast-list \
    --transfers 4 \
    --checkers 8 \
    --bwlimit 15M \
    --exclude "lost+found/**" \
    --log-file=/var/log/rclone-gdrive.log \
    --log-level INFO

echo "[$(date)] Google Drive Sync erfolgreich beendet!"
```
Ausführbar machen: `chmod +x /usr/local/bin/sync-pbs-to-gdrive.sh`

Schritt 4: Systemd-Timer für 04:30 Uhr morgens einrichten
Datei: `/etc/systemd/system/pbs-to-gdrive.service`
```ini
[Unit]
Description=Synchronize PBS Datastore to Google Drive
After=network-online.target

[Service]
Type=oneshot
ExecStart=/usr/local/bin/sync-pbs-to-gdrive.sh
```

Datei: `/etc/systemd/system/pbs-to-gdrive.timer`
```ini
[Unit]
Description=Daily Google Drive Offsite Backup Timer

[Timer]
OnCalendar=*-*-* 04:30:00
Persistent=true

[Install]
WantedBy=timers.target
```
Timer aktivieren: `systemctl daemon-reload && systemctl enable --now pbs-to-gdrive.timer`

Ergebnis:
Jeden Morgen um 04:30 Uhr werden alle neuen deduplizierten Chunks vollständig verschlüsselt
auf Google Drive gespiegelt. Das tägliche Upload-Volumen liegt typischerweise bei nur 200–800 MB!

KAPITEL 8: SICHERHEITSAUDIT & IDENTIFIZIERTE SCHWACHSTELLEN
====================================================================================================

Im Rahmen des Audits wurden folgende 6 kritische Sicherheitsaspekte identifiziert:

1. KLARTEXT-PASSWORT IM AUTH-PORTAL:
   In der Datei `/opt/auth-portal/data/config.json` steht:
   `"plainDefault": "ep123-washout"`
   Jeder, der Lesezugriff auf den Container CT 100 hat, kann das Master-Passwort im Klartext lesen.
   -> Maßnahme: Diese Zeile sofort aus der JSON-Datei entfernen.

2. PROXMOX NATIVE FIREWALL DEAKTIVIERT:
   Auf beiden Hosts meldet `pve-firewall status`: `Status: disabled/running`.
   Es existieren keinerlei Filterregeln. Sollte eine VM im Netzwerk kompromittiert werden,
   kann sie alle Ports auf PVE 1 und PVE 2 uneingeschränkt scannen und attackieren.

3. FEHLENDES 2FA AUF PROXMOX HYPERVISOR-EBENE:
   Die Datei `/etc/pve/tfa.cfg` ist auf beiden Hosts leer. Das Google Authenticator 2FA greift
   ausschließlich beim Zugriff über das Web-Portal. Wer im lokalen WLAN/LAN `https://192.168.178.169:8006`
   aufruft, benötigt lediglich das Root-Passwort ohne jeden zweiten Faktor!

4. ROOT SSH-LOGIN MIT PASSWORT:
   Beide Nodes erlauben SSH-Logins mit `root` und Passwort. Kein Fail2ban aktiv.
   -> Maßnahme: SSH-Keys hinterlegen und `PasswordAuthentication no` setzen.

5. AUSHEBELUNG VON CLICKJACKING-SCHUTZ:
   In `/opt/auth-portal/server.js` werden `x-frame-options` und `content-security-policy` gelöscht.
   Dies ist nötig, um Proxmox im Iframe anzuzeigen, birgt aber das Risiko, dass bösartige Webseiten
   die Session einbetten könnten.

6. FLATCHES NETZWERK (FLAT NETWORK):
   Minecraft-Traffic, Smart Home, Hypervisor-Management und Backup-Storage liegen ohne Isolation
   im selben Subnetz 192.168.178.0/24.

9.2. WIE DAS MIT DER FRITZ!BOX FUNKTIONIERT
----------------------------------------------------------------------------------------------------
Problem: Die FRITZ!Box beherrscht kein 802.1Q VLAN-Tagging auf ihren LAN-Ports.

Zwei funktionierende Lösungswege:

WEG A: Günstiger Smart-Managed Switch (~25–35 Euro, z. B. TP-Link TL-SG108E)
1. Port 1 des Switches verbindet die FRITZ!Box (Untagged VLAN 10 oder Default).
2. Port 2 geht an PVE 1 (Trunk-Port: VLAN 10, 20, 30, 40 getaggt).
3. Port 3 geht an PVE 2 (Trunk-Port: VLAN 10, 20, 30, 40 getaggt).
4. Das Routing zwischen den VLANs übernimmt entweder der Switch (wenn L3-fähig)
   oder eine Routing-VM.

WEG B: Kostenlose OPNsense / pfSense VM auf PVE 1 (Ohne Zusatzhardware)
1. Auf PVE 1 wird eine schlanke OPNsense VM installiert (2 vCPUs, 2 GB RAM).
2. WAN-Interface: Hängt an `vmbr0` und bekommt per DHCP eine IP von der FRITZ!Box (192.168.178.x).
3. LAN-Interface: Hängt an einer neuen virtuellen Bridge `vmbr1` (VLAN-Aware).
4. OPNsense spannt intern die 4 VLANs auf, verteilt DHCP-Adressen und blockiert mit echten
   Firewall-Regeln jeglichen unerlaubten Datenverkehr zwischen den Zonen!

9.3. KONFIGURATIONSBEISPIEL PROXMOX (/etc/network/interfaces)
----------------------------------------------------------------------------------------------------
So sieht die zukunftssichere Netzwerkkonfiguration auf PVE 1 aus:

```text
auto lo
iface lo inet loopback

iface nic0 inet manual

# Die Haupt-Bridge wird VLAN-Aware geschaltet:
auto vmbr0
iface vmbr0 inet manual
	bridge-ports nic0
	bridge-stp off
	bridge-fd 0
	bridge-vlan-aware yes
	bridge-vids 10 20 30 40

# Virtuelles Interface für Hypervisor-Management in VLAN 10:
auto vmbr0.10
iface vmbr0.10 inet static
	address 10.10.10.2/24
	gateway 10.10.10.1
	comment "PVE 1 Hypervisor Management"

# Virtuelles Interface für High-Speed Backup in VLAN 40:
auto vmbr0.40
iface vmbr0.40 inet static
	address 10.10.40.2/24
	comment "PBS Backup Interconnect"
```

Zuweisung an VMs:
Im Proxmox Web-Interface geht man in die jeweilige VM (z. B. VM 110) auf:
`Hardware -> Network Device (net0) -> Edit -> VLAN Tag: 20`
Sofort befindet sich die VM im isolierten Gaming-VLAN!
